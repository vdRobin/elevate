Services, IPC and flows

This page catalogs the application services, then traces the important runtime flows end to end: synchronisation on both targets, recalculation, history compliance checks, the Electron IPC tunnel, calls to remote services, and error handling.

Flow: desktop synchronisation

User clicks sync (DesktopSyncMenuComponent) → DesktopSyncService.sync(fastSync, forceSync, connectorType)
 1. gather in parallel: athlete, user settings, "sync from" time (fast sync only), most recent activity,
    connector info (Strava from DB, File from localStorage)
       Strava "sync from" = most recent activity startTimestamp * 1000
       File   "sync from" = connectorSyncDateTime[FILE].syncDateTime
 2. (re)subscribe to IpcSyncMessagesListener.syncEvents$ → handleSyncEvents()
 3. File connector: validate source folder, else WarningException "Go to connectors"
 4. IPC send startSync(connectorType, connectorInfo, athlete, userSettings, syncFromDateTime)
 5. on main's ack: isSyncing$.next(true)

Main process (desktop/) runs the connector, computes each activity with ActivityComputer
(@elevate/shared), and calls back into the renderer:
   findActivity(start, end)   → renderer queries ActivityDao.findByDatedSession  (dedup / update)
   findStreams(activityId)    → renderer returns deflated streams
   syncEvent(event)           → renderer handles:

 STARTED / STOPPED / GENERIC / STRAVA_CREDENTIALS_UPDATE → forwarded to syncEvents$ (UI)
     STRAVA_CREDENTIALS_UPDATE is also persisted by StravaConnectorInfoService
 ACTIVITY  → activityService.put(activity) → streamsService.put(deflated) → forward
             on DB error: stop sync, emit SYNC_ERROR_UPSERT_ACTIVITY_DATABASE, throw to ErrorHandler
 ERROR     → fatal codes (unauthorized, forbidden, quotas, unhandled, upsert, missing folder): forward + stop
             non-fatal codes (compute, multiple activities, already started, 404, timeout): forward
             unknown: throw SyncException
 COMPLETE  → put connectorSyncDateTime(now) → persist(true)
             → push insights (delta since previous last activity, or replace all)
             → isSyncing$.next(false) → forward

AppService: isSyncing$ false ⇒ historyChanges$ ⇒ verifyHistoryCompliance()

Flow: recalculation (desktop)

Recalculation re-runs the compute engine for stored activities with the current athlete settings and user settings. It is triggered by migrations that request it, by the recalculate bar after athlete settings changes, by the activity view, and by the advanced menu.

recalculate(activities, userSettings)
  guard: isRecalculating → reject WarningException "job already running"
  sequentially (Array.reduce over promises), for each activity:
     athleteSnapshotResolver.update()                ← reloads the athlete model EVERY activity
     snapshot = resolve(activity.startTime)
     streams = streamsService.getInflatedById(id)
     manual activity → only refresh athleteSnapshot, put()
     else            → IPC computeActivity(activity, snapshot, streams, userSettings) → put()
     recalculate$.next({ index, total, started: index==0, ended: index==last })
  isRecalculating = false
  verifyActivitiesWithSettingsLacking()
  persist(true)
  push all activities to insights (replace all)
DesktopSyncService maps recalculate$ started/ended to isSyncing$ true/false so the UI locks during the job.

Flow: history compliance checks

AppService.verifyHistoryCompliance() runs after app init (if synced) and after every sync end. It drives two shell bars.

  • Settings lacks: count({ settingsLack: true }) > 0 → activitiesWithSettingsLacks$ → recalculate bar suggests filling missing thresholds (ActivitiesSettingsLacksDialogComponent).
  • Consistency: for every activity, resolve the athlete snapshot for its date and compare with the stored snapshot through AthleteSnapshot.equals() → athleteSettingsConsistency$ → recalculate bar offers to recalculate. This is a full scan of all activities.

Flow: manual activity entry (desktop)

DesktopManualActivityDialogComponent builds a partial activity and calls ActivityService.createManualEntry(). It clones the input, sets times, converts imperial units, rejects overlaps with existing activities, attaches the athlete snapshot, computes average speed and pace and stress-per-hour scores, generates id as a SHA-256 of time plus Math.random() and hash as a SHA-256 of type, times, trainer and distance, then inserts.

The Electron IPC tunnel

Contract files are in modules/shared/electron/ and are compiled into both renderer and main.

  • BridgeApi: the surface exposed by desktop/src/pre-loading/pre-loader.ts as window.api. Typed helpers for window control and fs checks, plus generic invoke, receive and unsubscribe. invoke accepts any channel and wraps the arguments into an array, which is why payloads are positional arrays.
  • Channel: string enum of every channel.
  • IpcMessage: { channel, payload: any[] }. Payloads are positional arrays, destructured on the other side.
  • IpcTunnel: one class for both sides. Renderer to main uses bridgeApi.invoke, a proper request and response. Main to renderer uses webContents.send and waits for a single message on <channel>-response with ipcMain.once. Errors travel as values and are re-thrown if they are instanceof Error.

Architectural inversion

The database lives in the renderer, but the sync engine lives in main. Main must call back into the renderer (findActivity, findStreams) for every candidate activity, and push each result back (syncEvent). Sync throughput is bound by IPC round trips and by the renderer's single thread, and the UI must stay open for a sync to run. Main-to-renderer requests have no correlation id, so two concurrent requests on the same channel could receive each other's response.

Flow: application updates

  1. During startup, DesktopUpdateService.handleUpdate() sends updateApp(acceptPreReleases). Main returns an UpdateNotify or nothing.
  2. If there is an update, updateNotify$ drives DesktopUpdateBarComponent. Startup waits on updateHandledPromise, resolved by skipStaticUpdate() or by an error.
  3. Auto-updatable platforms receive updateDownloadProgress events until 100. Static platforms open the download and release pages in the browser and close the app.
  4. A setInterval calls checkForUpdate() every config.update.checkIntervalSec seconds, default 900.

Error handling and logging

ElevateErrorHandler.handleError(error)          (Angular ErrorHandler, per target)
  unwrap promise rejection (error.rejection)
  string → new Error(string)
  WarningException  → snackbar (message, optional action and duration) → STOP
  SyncException     → "Sync error: …"
  other ElevateException → "Elevate error: …"
  other             → error.message
  displayViewErrorAction(message, error)
      desktop:   snackbar "An unhandled error occurred" [Help] → ConfirmDialog with error.stack
                 → optional "Reset app" → second confirm → electronService.resetApp()
      extension: snackbar [View] → GotItDialog with error.stack
  onErrorHandled(error)  desktop prod: Sentry.captureException

Exception classes live in modules/shared/exceptions: ElevateException (base), WarningException (user-facing, non-fatal, optional action callback), SyncException, InconsistentParametersException, NotImplementedException. Domain validation errors use AppError (code plus message) from shared/models/app-error.model.ts, which is not an Error subclass.

Idiom used throughout: services throw WarningException to get a friendly snackbar from the global handler, and components rethrow anything else so the handler shows the stack. Promise rejections not caught by components reach the handler through Zone.js.
