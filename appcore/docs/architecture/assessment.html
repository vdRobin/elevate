Strengths and weaknesses

An assessment of appcore's architecture and code health. Defects below were found by reading the code at commit df9e2ceb; dependencies were not installed, so none were reproduced at runtime. Each one names the file and line so it can be checked.

Verdict

Appcore is a feature-rich, well-intentioned codebase with a clear core idea: one Angular app, two hosts, swapped at compile time through dependency injection. The domain modelling (dated athlete settings, snapshots, recalculation) is thoughtful. The weak points are durability and concurrency around the single in-memory database, an ageing toolchain several Angular majors behind, loose typing, uneven tests, and some privacy and HTML-injection exposure on desktop.

Strengths

  • Clean target abstraction. Abstract services as DI tokens plus three file replacements give two products from one tree. The other target's code is excluded from each bundle.
  • Layered persistence. Components, services, DAOs, DataStore, adapter. Swapping storage per target or for tests is a one-class change.
  • Shared domain library. @elevate/shared is compiled into renderer, Electron main and the extension, so models, sync events and the compute engine cannot drift.
  • Typed IPC vocabulary. One Channel enum and one IpcTunnel class for both sides.
  • Reproducible analytics. Dated athlete settings frozen into each activity as a snapshot make results reproducible and let the app detect stale computations.
  • Upgrade path. Ordered migrations, a "recalculation requested" flag, and restored backups re-entering the migration pipeline.
  • Local-first. Activity data stays on the machine. The app works offline apart from maps, fonts and help.
  • Streams stored apart. Heavy per-second data is lz-string compressed in its own collection, so activity lists stay light.
  • User-facing error taxonomy. WarningException with optional action gives consistent friendly messages through one global handler.
  • Lazy routes for every feature, and lint plus Prettier plus git hooks.

Weaknesses

  • Database durability. Whole-database saves after every write, live mutable documents returned from reads, no transactions, and destructive non-atomic restores.
  • Inverted sync topology. The database lives in the renderer while connectors run in main, so every candidate activity costs IPC round trips and the window must stay open.
  • Concurrency by booleans. Recalculation and sync locks are plain flags that are not reset on failure.
  • Outdated stack. Angular 14 (end of life since November 2023), flex-layout (deprecated), Moment, ComponentFactoryResolver, toPromise(), ngcc.
  • Loose typing. strict: false, positional any[] IPC payloads, untyped Loki collections in migrations.
  • Uneven tests. No specs for activities, connectors, advanced menus; one for the 5,600-line activity view; the extension DI graph barely exercised; the shared compute library is not run by appcore's Jest.
  • Privacy exposure. Full athlete model sent to the backend every 5 minutes; names, OS username and hostname attached to Sentry events.
  • HTML injection surface. Error stacks are injected as trusted HTML in dialogs.
  • Promise-chain style. Deep .then() chains with missing catch, the promise-constructor anti-pattern, and almost no async/await.
  • Dual wiring. Each target needs a boot module and a target module, plus template branching, so adding a cross-target service touches several files.

Good

The Electron window uses contextIsolation: true, nodeIntegration: false and a preload bridge. markdown-it runs with its default html: false, so release notes and help markdown cannot inject raw HTML.

Performance and scalability

  • Everything in memory. All activities and all streams load into the renderer at startup. Memory and startup time grow linearly with history. Streams are the bulk.
  • Save amplification. Each write calls saveDatabase. Desktop's incremental adapter limits the damage, but the extension adapter re-serialises the whole database to JSON and writes every collection on every write.
  • Full scans. Consistency checks iterate every activity and run after each sync. findSince filters on startTimestamp, which is not indexed.
  • Sequential recalculation. One activity at a time over IPC, and the athlete is re-fetched for every activity. Main has workers that could take batches.
  • Change detection. No OnPush in 92 components, while large tables and charts update on global events.
  • Bundle. Plotly, D3, MetricsGraphics, Mapbox, Moment, lodash and KaTeX are all present. The extension budget allows a 5 MB initial bundle.

Prioritised roadmap

  1. Fix data-safety defects. Reset recalculation locks in finally (defect 1). Make restores stage into a fresh database and swap on success, or back up first (defects 2 and 3). Add catch handlers that release sync state (defects 7 and 8).
  2. Close the injection path. Stop trusting error stacks as HTML and add a CSP.
  3. Reduce telemetry payloads. Strip personal data from check-in and Sentry.
  4. Harden the DataStore. Wait for LOADED on the extension, invalidate the collection cache on reload, clone defaults on insert, and return cloned documents from reads or document that they are live.
  5. Add an IPC correlation id for main-to-renderer requests and typed payload interfaces per channel.
  6. Raise the test floor. Run modules/shared specs, add specs for sync, backup and restore, and run the suite under both target modules.
  7. Upgrade incrementally. Angular 14 to 15 to 16 (drop ngcc), replace flex-layout with CSS, swap toPromise for firstValueFrom, then consider standalone components and inject().
  8. Turn on strictness gradually. Start with strictNullChecks on modules/shared, the code that runs in three runtimes.
  9. Revisit the sync topology. Move the database, or a read model of it, into main or a worker so sync no longer round-trips to the UI thread.
