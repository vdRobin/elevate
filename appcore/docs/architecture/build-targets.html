Build targets and bootstrapping

Appcore uses compile-time module substitution to produce two applications from one tree. This page explains the substitution mechanism, the resulting dependency injection graphs, the startup sequence and routing.

Build configurations

All four configurations live in angular.json under projects.app.architect.build.configurations. The default output path is ../dist/app/, but the host projects override it.

ConfigurationUsed byEnvironment fileNotable options

Host scripts call the CLI directly. For example the extension runs ng build --configuration=extension --output-path=../webextension/dist/app/. There is no production configuration, although serve.configurations.production references one, so ng serve --configuration=production fails.

File replacements: the core trick

Three files are placeholders in the source tree. Each configuration replaces them with a target-specific file.

PlaceholderDesktop replacementExtension replacementPlaceholder content
src/environments/environment.tsenvironment.desktop.ts or environment.desktop.prod.tsitself, or environment.prod.tsExtension dev settings.
src/app/boot/target-boot.module.tsdesktop-boot.module.tsextension-boot.module.tsOnly RouterModule.forRoot([]).
src/app/shared/modules/target/target.module.tsdesktop-target.module.tsextension-target.module.tsOnly RouterModule.forRoot([]).

The replacement files export a class with the same name (TargetBootModule, TargetModule) so the import sites in app.module.ts and shared.module.ts never change.

Consequence

The placeholder modules contain no providers. Anything compiled without a configuration, including the IDE language service, the type:check script and Jest, sees an app with no DataStore, no ActivityService and so on. Specs work around this by importing desktop-target.module or extension-target.module directly. Of the specs that import a target module, 44 import the desktop one and 3 the extension one, so the extension DI graph is barely tested.

The two dependency injection graphs

Abstract classes act as injection tokens. Each target module binds them to concrete classes with { provide: Abstract, useClass: Concrete }. Consumers inject the abstract type and, when they need target-only methods, cast it by annotating the parameter with the concrete type (for example @Inject(ActivityService) activityService: DesktopActivityService).

For AI assistants

Services are almost all module-provided (not providedIn: 'root'). A new service will not be injectable until you add it to the right providers array: SharedModule for both targets, desktop-target.module.ts or extension-target.module.ts for one target, or the feature module for feature-scoped services. The only providedIn: 'root' classes are the error handlers and ConsoleLoggerService.

Fragile point

The extension load path relies on a fixed 750 ms delay instead of the database LOADED event. On a large chrome.storage.local payload, early reads can hit an empty in-memory database, and findOne() on an empty collection inserts the default document. See defects.

Routing

Both routing modules use RouterModule.forRoot(routes, { useHash: true }), so URLs look like index.html#/fitnessTrend. Every route is lazy-loaded with loadChildren. The empty path redirects to activities. Route names are defined once in shared/models/app-routes.ts (AppRoutes). Toolbar and menu titles are derived from the route name with _.startCase, so renaming a route renames the UI label too.

Theming and styles

Themes are Angular Material SCSS themes in src/app/styles/themes/ (light.scss, dark.scss), wired by theming-setup.scss. The active theme is a class on body and on the CDK overlay container. Components that need theme colours provide a *.theme.scss mixin (for example app.component.theme.scss). The theme choice is stored in localStorage["theme"]. Global CSS also loads KaTeX, GitHub markdown and MetricsGraphics styles, plus Mapbox on desktop. Google Fonts (Material Icons, Roboto) load from the network in index.html, so the desktop app renders icons incorrectly when offline.
