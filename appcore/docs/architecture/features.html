Feature modules

Every routed feature is a lazy NgModule. Most are shared by both targets, and a few are desktop or extension only. Sizes and spec counts help locate complexity and risk.

The shared library modules/shared holds the heaviest domain logic. sync/compute/activity-computer.ts alone is 1,523 lines and stream-processor.ts 433 lines. It has a single spec file, and Jest in appcore does not run it because roots is src/ only. The desktop project tests part of this code from its side.

Activities

ActivitiesComponent is a Material table over all activities with paginator, sort, a debounced name search, sport and date filters, column picker by category (definitions in activity-columns.namespace.ts), CSV export with json2csv, and delete. Preferences and selected columns persist in localStorage. Above 35 selected columns it flags degraded performance. Data is loaded in full and filtered client side with MatTableDataSource. It reloads on AppService.historyChanges$. Opening a row goes through OpenResourceResolver.openActivity(), which routes to activity/:id on desktop and opens the Strava page on the extension.

Activity view (desktop)

ActivityViewComponent loads an activity by route id, user settings and display-processed streams (ProcessStreamMode.DISPLAY). Child components:

  • Map (activity-view-map): Mapbox GL with start, end and move markers, map type from user settings, token from MapTokenService.
  • Graph (activity-graph-chart.component.ts, 525 lines): Plotly multi-sensor chart. A bound selection publishes a range used by the debug stats and intervals.
  • Summary stats and stats groups: driven by declarative definitions in shared/models/stats/stats-def.namespace.ts (1,144 lines) and per-sport stat groups (cycling, running, swimming, default).
  • Sensors (shared/models/sensors): one class per metric with unit conversion and formatting (speed, pace, swim pace, power, heart rate, cadence, grade, elevation, distance, time).
  • Time in zones, peaks, best splits (computed in main through computeSplits), intervals (laps).
  • Edit dialog: name, type, trainer, notes. Flags: data quality issues with a clear action.

Fitness trend

FitnessService implements the impulse-response (Banister) model. prepare() filters activities by date and name patterns, skips types, and attaches the right stress score per activity: TRIMP or HRSS for heart rate, PSS for power (real or estimated, rides with a cycling FTP), RSS for running (running FTP), SSS for swimming (swim FTP). Flags for abnormal per-hour scores exclude a score. generateDailyStress() builds one entry per day including 14 preview days, then computeTrend() produces CTL (fitness), ATL (fatigue) and TSB (form). Configuration (FitnessTrendConfigModel: impulse mode, initial fitness and fatigue, ignore rules, estimated scores allowed) and toggles are in localStorage. UI: inputs, MetricsGraphics graph with D3 overlays, legend, table with CSV export, info and config dialogs, user guide.

Year progressions

YearProgressService computes cumulative per-day totals per year for distance, time, elevation and count, filtered by sport types and commute options, and rolling-window variants. Presets are stored in the yearProgressPresets collection. UI: MetricsGraphics graph, table, overview dialog, preset management dialogs, helper and user guide.

Athlete settings

Profile (gender, names, birth date, practice level, sports) and the dated settings manager. DatedAthleteSettingsManagerComponent lists periods, opens EditDatedAthleteSettingsDialogComponent, and calls AthleteService add, edit, remove or reset. SwimFtpHelperComponent derives swim FTP from a test. Any change makes stored snapshots inconsistent, which triggers the recalculate bar.

Zones settings

Edits zone boundaries per metric through ZonesService: add and remove with neighbour adjustment, compliance checks, save, reset, import and export as JSON. On the extension, saving sets localStorageMustBeCleared.

Global settings

GlobalSettingsService declares sections and options (checkbox, list, number) per build target. The component renders them, persists through UserSettingsService.updateOption(), and opens markdown help from assets/option-helpers. Most extension options control strava.com enhancements, so appcore only stores them.

Connectors (desktop)

  • Strava: the user enters their own Strava API client id and secret. StravaConnectorService.authenticate() runs the OAuth link in main (stravaLink) and stores tokens and the account. Options include updating names, types and commutes of existing activities. Disconnect clears credentials.
  • File: pick a folder; options for sub-directories, archive extraction and deletion, file renaming, sport detection. Stored in localStorage.
  • Garmin Connect: informational component only.

Both connector components extend ConnectorsComponent, which handles sync date display and navigation.

Recurring component patterns

  • Constructor injection with explicit @Inject(Token), often typed as the concrete target class.
  • Data loaded in ngOnInit with promise chains; errors rethrown to the global handler, except WarningException.
  • Default change detection everywhere (no OnPush). Charts redraw on WindowService and SideNavService events.
  • Subscriptions stored in fields and released in ngOnDestroy. There is no takeUntil or async pipe pattern.
  • Dialogs opened with MIN_WIDTH and MAX_WIDTH static constants on the dialog class; dialog data typed with a *DataModel class.
  • Target branching in templates through buildTarget === BuildTarget.EXTENSION when a whole component is not worth duplicating.
