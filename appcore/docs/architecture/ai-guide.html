AI working guide

Instructions for AI coding assistants, and humans, making changes in appcore. Follow the rules, use the playbook that matches the change, and run the checklist before finishing.

Golden rules

  1. Think in two targets. Every change compiles into the desktop app and the extension. Before editing, find whether a desktop-* and an extension-* variant exist for the file, module, service or component.
  2. Inject abstractions. Depend on ActivityService, SyncService, DataStore and similar abstract tokens. Annotate with a concrete type only in target-specific code.
  3. Register providers explicitly. Services are module-provided. Shared goes to SharedModule, target-specific to desktop-target.module.ts or extension-target.module.ts, shell and lifecycle bindings to boot/desktop-boot.module.ts or boot/extension-boot.module.ts, feature-scoped to the feature module.
  4. Never import desktop code from shared code. Files under src/app/desktop/ must only be imported from desktop-target, desktop-boot or other desktop files, otherwise Electron-only services leak into the extension bundle. The reverse applies to src/app/extension/. One shared file already breaks this rule (shared/services/file-connector-info/file-connector-info.service.ts imports ElectronService); it only works because only desktop code injects it. Do not add more.
  5. Keep modules/shared runtime-neutral. It runs in the browser, in Electron main and in the extension. No Angular, no DOM-only APIs without guards, no Node-only APIs (fs resolves to an empty stub in appcore). Import it through the @elevate/shared/... aliases.
  6. Treat Loki documents as live. Objects returned by DAOs are the database's own objects. Clone (_.cloneDeep) before speculative edits, and call update or put to persist.
  7. Pass clones of defaults. Never insert a static DEFAULT_MODEL by reference.
  8. Release locks and flags in every path. Any code that sets isSyncing$, isRecalculating or similar must reset it on failure too.
  9. Prefer WarningException for user-facing, expected failures. The global handler shows it as a snackbar. Throw other errors only for real bugs.
  10. Do not render untrusted text as HTML. Dialog content and title are trusted with bypassSecurityTrustHtml. Escape any dynamic value placed in them.
  11. Match existing style. Prettier (print width 120, double quotes, no trailing commas, arrowParens: avoid), app- selector prefix, explicit @Inject() on constructor params, public and private modifiers spelled out.
  12. New code may use async/await but must return Promise like its neighbours. Do not convert unrelated chains while fixing something else.

Playbooks

Add a route and feature module
  1. Add the path to shared/models/app-routes.ts. The name becomes the title through _.startCase.
  2. Create <feature>.module.ts importing CoreModule and a <feature>-routing.module.ts with RouterModule.forChild([{ path: "", component }]).
  3. Add a lazy route in shared/modules/routing/desktop-routing.module.ts and/or extension-routing.module.ts.
  4. Add a menu entry in shared/services/menu-items/impl/desktop-menu-items-provider.service.ts and/or the extension one.
  5. If the page needs activities, gate it on SyncState and use <app-activities-required>.
  6. Subscribe to AppService.historyChanges$ if the page must refresh after syncs, and unsubscribe in ngOnDestroy.
Add a target-specific service
  1. Create abstract class FooService with the shared logic and abstract methods, constructor protected.
  2. Create DesktopFooService and ExtensionFooService with @Injectable(), repeating every constructor parameter with @Inject().
  3. Bind { provide: FooService, useClass: DesktopFooService } in desktop-target.module.ts, and the extension equivalent.
  4. In specs, import the target module you test (desktop-target.module or extension-target.module) and provide { provide: DataStore, useClass: TestingDataStore }.
Add a persisted collection
  1. Define the model in modules/shared/models if shared, otherwise in src/app/shared/models.
  2. Create FooDao extends BaseDao<Foo> with static readonly COLLECTION_DEF = new CollectionDef("foo", { unique: ["id"], indices: [...] }).
  3. Return a fresh object or array from getDefaultStorageValue(). Do not return a shared static.
  4. Provide the DAO in the right module and wrap it in a service; components should not use DAOs directly.
  5. Decide whether backups must include it. Desktop backups include every non-empty collection automatically; the extension backup lists fields explicitly in ExtensionSyncService.prepareForExport().
  6. If existing users need data reshaped, add a desktop migration.
Add a desktop migration
  1. Create src/app/desktop/migration/upgrade_X_Y_Z/upgrade_X_Y_Z.ts with export class Upgrade_X_Y_Z extends DesktopMigration (pre-releases use $, for example Upgrade_7_0_0$beta_3).
  2. Set version to the release that ships it, a description, and requiresRecalculation.
  3. In upgrade(db, injector), work on db.getCollection("..."), guard for missing collections, make the operation idempotent, then return this.saveDatabase(db).
  4. Append it at the end of DesktopRegisteredMigrations.LIST, which must stay sorted by version.
  5. Test it by downgrading version in ipc.storage.json in the user data folder.
Add a user setting
  1. Add the field and its default to DesktopUserSettings and/or ExtensionUserSettings (both the class field and DEFAULT_MODEL) in modules/shared/models/user-settings/user-settings.namespace.ts.
  2. Add the option definition in GlobalSettingsService for the target.
  3. Add assets/option-helpers/<key>.md if it has help.
  4. Existing users' stored settings will not have the field. Read it with a fallback, or add a migration on desktop.
  5. If the setting changes computed stats, request a recalculation.
Add an IPC channel
  1. Add the name to Channel in modules/shared/electron/channels.enum.ts.
  2. Renderer to main: call ipcTunnelService.send<IpcMessage, R>(new IpcMessage(Channel.x, ...args)) from a desktop service. Implement the handler in desktop/src with the main-side tunnel on(), destructuring the payload array in the same order.
  3. Main to renderer: register ipcTunnelService.on(Channel.x, payload => ...) once, in a singleton service constructor, and return a value or a promise.
  4. No preload change is needed: desktop/src/pre-loading/pre-loader.ts exposes a generic invoke(channel, ...args) and receive(channel, listener) with no channel allowlist. Add a typed helper to BridgeApi only for direct shell calls.
  5. Do not run concurrent main-to-renderer requests on one channel until a correlation id exists.
Change the Activity model or computed stats
  1. Edit modules/shared/models/sync/activity.model.ts and the computation in modules/shared/sync/compute/.
  2. Check consumers in three places: appcore (activities columns in activity-columns.namespace.ts, activity view stats in stats-def.namespace.ts, fitness and year progress), desktop/, and webextension/.
  3. Stored activities keep the old shape. Add a desktop migration with requiresRecalculation: true, or handle missing fields.
  4. Run the desktop project's tests, which cover the compute engine.
Add a shell widget variant

Follow the existing pattern: an abstract @Component({ template: "" }) base plus an InjectionToken, an anchor directive declared in AppModule, a <ng-container appX> in app.component.html, creation in AppComponent.initApp(), and concrete components declared and provided with useValue in both boot modules.

Handle a new sync error code (desktop)
  1. Add the static ErrorSyncEvent definition in modules/shared/sync/events/error-sync.event.ts.
  2. Classify it in DesktopSyncService.handleErrorSyncEvents() as fatal (forward and stop) or non-fatal (forward). Unclassified codes throw.
  3. Display it in DesktopErrorsSyncDetailsDialogComponent if needed.

Pitfalls

  • Timestamps: startTimestamp is seconds; sync date times and Date.now() are milliseconds.
  • findOne inserts: calling it on an empty singleton collection creates the default document in memory.
  • AthleteSnapshotResolverService.resolve() throws unless update() was awaited first.
  • Placeholder modules: the IDE and type:check see empty target modules; a missing provider shows only at runtime or in specs that import a real target module.
  • Desktop dev builds are JIT (aot: false). Build desktop-prod or extension to catch template type errors.
  • Route names are UI labels. Renaming an AppRoutes value changes titles and menu labels.
  • Extension sync reloads the page when done, so in-memory state does not survive it.
  • Global scripts: D3 and MetricsGraphics are loaded as global scripts in angular.json, not imported as modules.
  • Specs run under jsdom with window.require, localStorage and Mapbox mocked in src/test.ts. chrome.* is not mocked globally.
  • Shared spec files outside src/ do not run in appcore's Jest.

Commands

# one-time, from the repository root (installs all three projects)
npm install

# appcore only (run inside appcore/)
npm test                    # Jest with coverage (HTML report in coverage/)
npm run type:check          # tsc on app and spec tsconfigs (placeholder target modules)
npm run lint                # angular-eslint with --fix

# build appcore for a target (inside appcore/)
npx ng build --configuration=desktop-prod
npx ng build --configuration=extension-prod

# full builds through the hosts
cd desktop && npm start                    # watch appcore + electron into desktop/dist
cd desktop && npm run launch:dev:app      # in another terminal
cd webextension && npm start              # watch into webextension/dist, load unpacked

# repository root
npm test                                  # desktop + appcore + webextension tests
npm run type:check:desktop                # appcore + desktop type checks
npm run type:check:extension              # appcore + webextension type checks

Before finishing a change

  1. Did you handle both targets, or confirm the change is single-target and placed under desktop/ or extension/?
  2. Is every new service registered in a module that both targets (or the right target) import?
  3. Do specs pass, and do new specs import the matching target module with TestingDataStore?
  4. Does npm run type:check pass, and does a production build of each affected target pass?
  5. Do stored documents from older versions still load, or is there a migration?
  6. Are flags and subjects released on error paths? Is every promise chain terminated with a catch or returned to a caller that has one?
  7. Is any dynamic text placed in dialog HTML escaped?
  8. If the Activity model or compute engine changed, did you check desktop/ and webextension/ consumers?
